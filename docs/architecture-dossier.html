System Overview

BandMusicGames is a native SwiftUI/SpriteKit iOS app (ios/BandMusicGames) with a parallel, structurally-similar web build (index.html + js/, deployed to Cloudflare Pages) that is not the same code path as the native lobby. The native app's single @main entry point currently hard-boots straight into the Lizzy McGuire game for playtesting rather than the jukebox lobby — a reversible flag, not a redesign. Song selection in the lobby routes to either a native SwiftUI/SpriteKit game view or, for anything not explicitly recognized, a generic WKWebView-hosted web game.

Naming note

The file is called LizzyMcGuireGameView.swift, the in-app UI brands it "Nara's Room", and its engine class is HalfCourtHeroScene — a half-court 1-on-1 basketball minigame. All three names refer to the same feature. This dossier treats them as one system in §2.

§1.1

Game Lobby — Boot & App Shell

The lobby is the native jukebox-style song/game picker. Before reaching it, three boot-priority flags in the App struct decide what the user actually sees first.

The @main entry point and only Scene. Owns the two app-lifetime environment objects (SpotifyAuthManager, AppleMusicManager) and picks the root view from a fixed if/else-if priority chain over three private flags — there is no runtime navigation state involved.

ForceLandscape / OrientationController App/ForceLandscape.swift:7-39

A ViewModifier (.forceLandscape()) plus a stateless controller enum that writes AppDelegate.orientationLock and forces every connected window scene to re-layout immediately — the per-screen mechanism that lets only the Lizzy McGuire screen rotate while the rest of the app stays portrait.

Notable logic

  • A requestGeometryUpdate failure is only printed in DEBUG builds — a plist orientation misconfiguration would fail silently in release. App/ForceLandscape.swift:32-36

ContentView — Lobby Container & Router

ContentView Views/ContentView.swift:3-231

Renders JukeboxView over a themed background, owns song-selection/playback timing, and routes the chosen Song into a native game or a web-hosted fallback via two stacked fullScreenCover modifiers.

Routing table — nativeGame(for:) ContentView.swift:135-152

Notable logic

  • handlePlay() only forces the Spotify connect sheet when the target is a web game and Spotify isn't connected — native games launch with no Spotify connection required. ContentView.swift:99-111
  • Play fires auth.playTrack(...) immediately but delays presenting the game by a hardcoded 1.54s (Task.sleep(nanoseconds: 1_540_000_000)) so the jukebox's needle-drop animation has time to play; the task is cancelled on re-entry and on disappear. ContentView.swift:113-127, 68-69
  • onAppear runs a one-shot auto-launch (guarded by didAutoLaunch + a static autoLaunchLizzyLobby flag) that finds the first catalog song resolving to .lizzyMcGuire and immediately sets launchingSong — bypassing the normal select-then-play flow. ContentView.swift:72-80
  • spotifyErrorOverlay renders different recovery actions per PlaybackError case: WAKE SPOTIFY (.noDevice) retries after a 4s delay; OPEN IN SPOTIFY (.notPremium) deep-links via auth.lastAttemptedUri. ContentView.swift:171-206
§1.3

Song — Catalog Data Model

Song Models/Song.swift:3-70

Identifiable/Hashable value type for one lobby entry. A hardcoded static catalog of 3 entries (goon / FOR CUTTING GRASS, francis / FRANCIS, narasroom / LIZZY MCGUIRE) is the app's entire content database — no persistence or network fetch layer exists here.

  • Hashable/Equatable are id-only, which matters because Song is the identity type for fullScreenCover(item:) on launchingSong. Models/Song.swift:16-17
  • Color(hex:) strips non-alphanumerics, parses via Scanner.scanHexInt64, and bit-shifts out R/G/B — no alpha channel or 3-digit shorthand support. Models/Song.swift:61-69
  • Each entry independently feeds three different subsystems: id/gameUrl/title → routing, trackUri → Spotify playback, appleMusicId → the MusicKit path. Models/Song.swift:4-12, 22-54

GameSheetView / GameWebView — Web Game Host

GameSheetView / GameWebView Views/GameWebView.swift:7-113

Fallback presentation path for any Song the native router doesn't recognize: wraps a WKWebView loading the song's remote gameUrl, authenticated via a Spotify-token cookie, with a manual close button since the view is full-screen with no native chrome.

  • Writes an sp_token cookie (token present) or a fallback sp_skip=1 cookie, scoped to domain .bandmusicgames.party — the page load only fires inside the cookie-set completion handler, guaranteeing the cookie is present on first request. GameWebView.swift:68-98
  • Coordinator.webView(_:decidePolicyFor:decisionHandler:) unconditionally allows every navigation — there is no domain allowlist once the game page loads. GameWebView.swift:104-111

JukeboxView — Selector Engine

The visual and interaction core of the lobby, 1,294 lines. It composes a header, a "dial" card (a decorative Canvas illustration, not a rotary control), a vertical selection list, transport controls, and Spotify status.

⚠ Correction to initial framing

A full-file grep for Gesture|.gesture(|onTapGesture|DragGesture|RotationGesture|MagnificationGesture returns zero matches. There is no drag/rotate/swipe recognizer anywhere in this file and no inertia/momentum system driving a spinning dial from touch. Every selection change is a discrete SwiftUI Button tap routed through select(_:) / navigate(backward:). The only "physics" in the file is decorative, clock-driven wobble/jitter math inside the Canvas illustration — it reacts to time, not touch.

§1.7

Services Layer (Managers)

SpotifyAuthManager Managers/SpotifyAuthManager.swift:7-364

MainActor ObservableObject owning the full Spotify OAuth (PKCE) flow via ASWebAuthenticationSession, token persistence/refresh, and Spotify Connect playback control. Created once app-wide; the single source of truth for whether the app can control Spotify playback.

  • PKCE flow: a random 32-byte verifier is base64url-encoded, SHA256-hashed as the S256 challenge, sent to /authorize, then the raw verifier is POSTed back on code exchange. SpotifyAuthManager.swift:63-75, 335-350, 298-333
  • init() reconstructs connection state from UserDefaults without a network call — an expired token with a refresh token present optimistically marks connected and defers the actual refresh to the first playTrack() call, avoiding a race with SwiftUI's onAppear. SpotifyAuthManager.swift:48-59
  • HTTP status mapping: 204 success · 401 refresh-and-retry-once · 403 → .notPremium · 404 → .noDevice (explicitly does not auto-open Spotify mid-game) · default → .unknown. SpotifyAuthManager.swift:145-170
  • refreshToken() uses a single-flight Task guard so concurrent callers await the same in-flight request rather than issuing two POSTs against a refresh token Spotify may rotate. SpotifyAuthManager.swift:249-296
AppleMusicManager Managers/AppleMusicManager.swift:8-108

MainActor wrapper around MusicKit's ApplicationMusicPlayer — an alternate playback backend to Spotify Connect, activated as isPreferred from the Spotify error banner's "switch to Apple Music" recovery path.

  • activateAsPreferred() sleeps 300ms after authorization because canPlayCatalog updates asynchronously via a subscription stream, not synchronously with the auth call. AppleMusicManager.swift:34-44
  • startSubscriptionMonitor() auto-flips isPreferred back to false if a lapsed subscription is detected mid-session, falling back to Spotify. AppleMusicManager.swift:97-106
HapticManager Managers/HapticManager.swift:3-21

Stateless enum namespace over three UIKit feedback generators (selection/impact/notification). Called by name directly — no dependency injection.

  • Every call constructs and fires a fresh generator rather than pre-warming one — a deliberate latency-for-simplicity tradeoff. HapticManager.swift:4-20
LobbyPreviewPlayer Managers/LobbyPreviewPlayer.swift:8-108

Per-ContentView @StateObject that plays 30s iTunes preview clips on an endless cycle while disconnected from Spotify, so the lobby isn't silent.

  • runCycle() is an infinite loop: play a resolved preview for a fixed 20s, or on a resolution miss, advance after only 3s to keep the cycle moving. LobbyPreviewPlayer.swift:39-63
  • fetchPreview(for:) queries the public iTunes Search API with two-pass soft artist matching, falling back to the first result with any preview URL rather than returning nothing. LobbyPreviewPlayer.swift:78-106

Web Lobby — Parallel Implementation

Out of scope, noted for completeness

index.html + js/lobby.js (663 lines) implement a second, structurally similar jukebox dial in vanilla JS/Canvas, deployed independently to Cloudflare Pages (npm run deploy → wrangler pages deploy). It shares the song-catalog-and-dial concept with the native lobby but is a fully separate codebase with its own SONGS array and its own LobbyAuth/haptics shims — not the code path documented in §1.1–§1.7. §2.3

Control System — HoopLand vs. JumpBall

⚠ Correction to the design spec

The design spec (docs/superpowers/specs/2026-06-30-nara-control-modes-landscape-design.md) proposed a dedicated HalfCourtControlsNode class with onPass/onShootDown/onShootUp/onJump/onSteal/onBlock callback closures, and a retired gesture classifier named classifyRightGesture/isActionZone. Neither exists in the shipped code (grep-verified repo-wide). What actually shipped:

  • ControlButtonNode — a passive, reusable SKNode circle with a label + optional charge ring. It has no callback properties; it only exposes a geometric hitTest(_:). HalfCourtHeroScene.swift:2204-2306
  • ControlContext enum + a computed controlContext property is the actual mode/state router. HalfCourtHeroScene.swift:100-115
  • Routing lives directly in handlePrimaryDown(_:) / handleSecondaryDown() / refreshControlButtons(), switching on controlContext. HalfCourtHeroScene.swift:1108-1172
ControlContext state machine HalfCourtHeroScene.swift:100-115

The single computed property deciding what the two on-screen buttons currently mean, derived from phase + playState + possession + controlStyle.

Touch handling & button dispatch HalfCourtHeroScene.swift:1019-1172

Routes raw touches into three priority channels: Knicks-poster easter egg → control-button hit-test → left-thumb joystick.

  • Hit-testing order is load-bearing and explicitly commented: "on-screen control buttons win hit-testing first," preventing a tap near the button region from also registering as joystick placement. HalfCourtHeroScene.swift:1040-1042
  • On touch release, the charge value is captured into a local before tapMeterFill resets to 0 — explicitly flagged in-code as load-bearing ordering, since resetting first would always release a 0-charge shot. HalfCourtHeroScene.swift:1081-1088
  • HoopLand's buttonA is hold-to-charge SHOOT with a green/perfect timing ring; JumpBall's buttonA is single-tap JUMP with the ring hidden entirely, since accuracy there comes from openness, not timing. HalfCourtHeroScene.swift:1143-1151
  • If controlContext changes away from a charge-eligible state mid-press (possession flips while SHOOT is held), refreshControlButtons force-clears the touch and un-presses the button to prevent a stuck charging state. HalfCourtHeroScene.swift:1167-1171
JoystickNode HalfCourtHeroScene.swift:2308-2358

Floating left-thumb movement stick, repositioning to wherever the thumb first touches down (not fixed-position).

  • DEAD SIGNAL vector is computed and exposed but updateHuman() does not read it — movement is recomputed independently from raw touch-location deltas. The node's normalized vector output is visual-only in the current build. HalfCourtHeroScene.swift:2341-2351, cross-ref 747-781
§2.4

Shot Mechanics & Physics

Shot charge/power meter HalfCourtHeroScene.swift:143-146, 708-745, 1110-1125

Hold-to-charge meter driving HoopLand shot quality; the same routine also drives the CPU's block-timing fill during .awayShot.

  • Charge caps at 1.2 (20% overcharge) so "too late" releases are distinguishable from perfect timing. HalfCourtHeroScene.swift:720
  • Meter decays continuously on early release rather than snapping to 0, giving analog feedback. HalfCourtHeroScene.swift:722
launchVelocity(from:to:flightTime:) / performLaunch HalfCourtHeroScene.swift:1555-1591

A closed-form projectile-motion solver — not trial-and-error — converting a target point + desired flight duration into an initial physics velocity.

  • Kinematic solve: vx = dx/t; vy = dy/t + 0.5·g·t — every shot lands exactly at (rimX + errorOffset, rimY) after flightTime seconds regardless of distance. HalfCourtHeroScene.swift:1586-1591
  • flightTime scales with distance (0.82 + dist/700s) so long threes arc longer than layups. HalfCourtHeroScene.swift:1565
  • gravityPointsPerSec2 converts SpriteKit's gravity (m/s², 150pt/m) into points/s². HalfCourtHeroScene.swift:1581-1584
shotAccuracy() / shotError() HalfCourtHeroScene.swift:1472-1516

Core deterministic scoring model shared identically by HoopLand and JumpBall, despite their different input UX.

CPUState machine — updateCPU HalfCourtHeroScene.swift:93-98, 783-830

Drives the ball-handling CPU through bringUp(spot) → dribbling(until) → shooting, reusing the same launchVelocity/performLaunch path as human shots.
